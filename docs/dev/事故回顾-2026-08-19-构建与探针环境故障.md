## 二、根因链分析

### 表面根因（直接触发）

1. **`--import` 在本机长时间无输出/挂起**（凌晨 04:13 首次出现"卡在 94%/16%"，当时误判为完成即绕过；今天复发）。
   - 后果 A：中途被杀 → `.godot/mono/temp/obj` 留下**损坏缓存** → 构建写入被拒（MSB3491）。
   - 后果 B：资源导入不完整 → 运行时 Godot 检测资源状态不一致 → **TestSuite 实体构造 signal 11 原生崩溃**。
2. **构建失败后诊断方向错误**：先怀疑"进程锁"（枚举进程 ×3、build-server shutdown、删单文件、查 ACL、沙箱开关），**实际一步 `rm -rf obj/Debug` 即解决**。8 分钟里 6 步是弯路。
3. **探针崩溃排查发散**：signal 11 无 C# 栈，逐个怀疑贴图→.ctex→.tres→代码→TRAE 改动，**没有第一时间想到"obj 被删后需重跑 import 恢复资源一致性"**——跑了 6-8 次无效二分后才回到 import。

### 深层根因（为什么会这样）

1. **验证工具链与环境状态强耦合，且脆弱性未沉淀**：
   - 探针体系依赖"Godot 资源导入一致性"，但本机 `--import` 不稳定——这是**已知问题却无记录、无预案**（凌晨已出现，未写入文档/记忆）。
2. **多 Agent 协作的隐性排查成本**：
   - TRAE 的 M1-PERF + 敌人四类 + TestProbes（07:29）大改全在工作树（未提交）——排查时**无法快速隔离"我的改动 vs TRAE 改动"**，多次怀疑 TRAE 代码，分散注意力。
   - 若当时先做"隔离实验"（临时禁用我的贴图加载验证），可更快排除自身。
3. **诊断方法论缺失"先环境后代码"原则**：
   - 构建/探针异常时，应先验证**环境基线**（import 一致性、obj 缓存干净）→ 再二分代码。本次反了：先怀疑代码/进程，最后才回 import。
4. **每次排障都在"重新试错"，没有固定动作序列**：
   - 环境类故障的标准动作（import → build → probe 固定顺序 + 已知坑速查表）缺失，导致每次遇到同类问题都从头摸索。

## 四、改进预案（写入纪律，下次直接照做）

### 1. 已知环境问题速查表（新增到 docs/dev/BugLog.md 或本文附录）
| 症状 | 根因 | 标准动作 |
|---|---|---|
| `--import` 长时间无输出 | 本机 Godot headless import 慢/挂起（已知） | **等 ≥5 分钟**（后台跑，勿中断）；仍无则 `rm -rf .godot/imported` 重导 |
| 构建 MSB3491（obj 写入 denied） | obj 缓存损坏（import 中断残留） | **直接 `rm -rf .godot/mono/temp/obj`** 重建（不查进程/ACL） |
| 探针 signal 11（实体构造崩） | 资源导入不一致 / 删 obj 后未重导 | **先完整跑一次 `--import`**，再二分代码 |
| 新素材加载异常 | 源文件与 .import 版本不一致 | 固定流程：新素材入库前必须 `--import` 成功 |

### 2. 固定验证序列（每次改动后按序执行）
```
1. dotnet build（失败 → 直接 rm obj/Debug 重建）
2. 有新增/替换素材 → Godot --headless --import（后台，等 ≥5 分钟）
3. 跑探针全量（仍崩 → 重跑 import → 仍崩才二分代码）
4. 全绿 → 提交
```

### 3. 多 Agent 排查纪律
- 怀疑"他人改动"引入问题时，先做**自身隔离实验**（临时禁用我的改动）快速排除，再向 TRAE/用户反馈具体文件+行号。
- 不基于"未提交工作树"做崩溃归属判断（TRAE 改动未提交，无法 diff 定位时如实标注"待 TRAE 侧确认"）。

### 4. 环境问题沉淀
- 凌晨/今天两次 import 卡死的经验，**立即补记**到记忆与 BugLog（本次已做）。
- 每次会话开头检查：`.godot` 是否有残留 import/build 进程（避免旧句柄污染新任务）。

## 五、本次事故结论

1. **技术根因**：Godot headless `--import` 在本机不稳定（长时间无输出），导致 obj 缓存损坏（构建失败）+ 资源状态不一致（探针崩溃）——**两次环境故障同源**。
2. **流程根因**：缺乏"环境已知问题速查表"与"先环境后代码"的排障顺序，25 分钟排障中大部分是在重新试错。
3. **未定位项**：探针崩溃是否还叠加 TRAE 07:29 改动的因素——需在 import 完整 + 探针恢复后复核；若仍崩，转 TRAE 侧排查（附文件/行号）。
4. **收获**：素材产出+代码接入本身零返工（一次通过），故障全在环境层——加固环境纪律后，此类时间黑洞可压缩 80%。
