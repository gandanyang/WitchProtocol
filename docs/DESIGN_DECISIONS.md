## D-001（2026-08-19）地基阶段 → 第一章垂直切片

**决策**：当前项目处于「地基阶段」，工程骨架 + 核心系统 + 测试体系已就位（5/5 探针 PASS）。下一阶段目标是做出一条**可完整游玩的弹幕战斗闭环**（垂直切片），而非继续堆系统。

**理由**：从「加功能」转向「证明好玩」。先让玩家玩到一条完整的弹幕战斗体验，再扩展内容。

**约束**：垂直切片优先保证：弹幕手感（对象池 + Pattern）→ 玩家闪避 → 敌方弹幕 → 记忆碎片收集 → 一个情感收束点。新增系统前先过「新增系统检查清单」（见 `docs/开发约束与架构入口.md`）。

## D-002（2026-08-19）技术栈：Godot 4.7 + C#

**决策**：本工程采用 **Godot 4.7.1 mono + C#/.NET 8**（区别于参考项目 ReturnToStars 的 Phaser 3 + TS）。

**理由**：二次元弹幕 RPG 需要稳定高性能的 2D 渲染与对象池热路径，C# 静态类型更适合弹幕数学与数据驱动；Godot 4.7 为 LTS 前的成熟版本。

**约束**：不改引擎 / 不引入后端。渲染见 D-005（原 Forward Plus，2026-08-19 制作人拍板切换）。

## D-005（2026-08-19）渲染器：Forward Plus → GL Compatibility（2D 弹幕性能）

**决策**：项目渲染器由 Forward Plus 切换为 **GL Compatibility**（`renderer/rendering_method="gl_compatibility"`）。

**理由**：二次元弹幕为 2D 重负载（大量 sprite + shader + 对象池热路径），Forward Plus 的 3D 重管线导致明显掉帧；GL Compatibility 为 2D 专用渲染，帧率大幅提升且兼容性最好。

**约束**：现有 canvas_item shader（remove_dark / remove_white）完全兼容；探针为 headless 纯逻辑不受影响；后续若引入 3D 需求需重新评估。

## D-004（2026-08-19）沙箱测试时 user:// 重定向

**决策**：TRAE 沙箱下，`tools/run_tests.ps1` 把 `APPDATA` 重定向到工程内 `.godot/userhome`，让 `user://`（存档/日志/测试报告）落在工程内、不入库。

**理由**：沙箱禁止写系统 AppData，导致 save 探针失败；重定向后 5 探针全绿且无污染。

**约束**：`.godot/` 已在 `.gitignore`，重定向目录不会入库。正式玩家的 `user://` 仍是 `AppData/Roaming/magicThunder`，不受影响。

## D-006（2026-08-19）产品定位：高表现力二次元弹幕动作 RPG

**决策**：产品定位正式定为「**高表现力二次元弹幕动作 RPG**」，不是纯硬核弹幕游戏。核心设计原则：**「视觉可以很难，操作不必那么难」**——降低「躲弹幕」的操作门槛，提高「看弹幕、造弹幕、玩角色」的爽感；硬核弹幕仅作为高难玩法存在，不是整个游戏的门槛。核心标签：魔女 / 弹幕海 / 技能演出 / Boss 机制 / 角色养成 / 音乐 / 剧情。

**理由**：二次元玩家偏好漂亮角色、漂亮技能、弹幕海、Boss 演出与音乐；纯硬核（精确判定 / 极限走位 / 一失误就死）与养成爽感是不同人群。两头拉满易两头不讨好；「养成 × 爽快弹幕」更贴近二次元大制作边缘，也更适合移动端。

**约束**：此后每次战斗设计先问「**这是在让玩家爽，还是单纯让玩家更难？**」——若只是更难、而未增加任何爽感增量（视觉 / 操作 / 成长 / 角色 / 剧情），砍掉。本决策与长期规划 v1.0（`docs/弹幕海与Boss演出系统-长期规划-v1.0.md`）兼容叠加，不推翻。

## D-007（2026-08-19）软辅助容错系统（Soft Dodge）

**决策**：引入软辅助（不是"玩家附近子弹自动飞走"）：玩家受到敌弹威胁时，仅对**低危弹**做轻微偏移 / 移动方向危险弹修正 / 擦弹判定点的极小安全偏移；高危与核心机制不做。危险分四级：一级普通小怪弹→软修正；二级精英弹→轻微辅助；三级 Boss 核心机制→不辅助；四级 Boss 终焉→完全手动。

**理由**：降低操作门槛但不显假（不做"碰到但无伤"，那会很假）；给玩家「我操作很精准」的体感，实际系统在兜底；天然适合手机触屏。难度依然有层次。

**约束**：实现上给 `PatternSpec` / `Bullet` 挂 **危险等级（DangerTier）**，soft-dodge 仅处理 1~2 级，3~4 级完全手动；**禁止对全量弹（5000 级）逐帧做 soft-dodge 计算**——只处理危险子集或抽样，守住 M1-PERF 压测红线；改动须过探针（20/20 全绿）。

## D-008（2026-08-19）难度三档：Casual / Standard / Hardcore

**决策**：同一套战斗系统服务三档难度——**Casual**（软追踪强、判定友好、Boss 预警明显、资源掉落舒服、允许复活）/ **Standard**（适度软追踪、正常判定、Boss 机制完整）/ **Hardcore**（软辅助极低、判定严格、Boss 弹幕强化、特殊挑战奖励）。

**理由**：把难度交给玩家决定；「硬核」放到内容层面而非基础操作——Boss 机制狠、剧情狠、后期挑战狠。玩家第一遍很爽、高难对线、熟练后挑战无伤，各自选择。

**约束**：难度为**持久设置**→ 按 `docs/dev/SaveSystem.md` 纪律**新增字段 + EnsureDefaults 兜底 + 不升 SaveVersion**；默认 Standard。影响范围：软辅助强度、弹速/密度系数、判定、复活、掉落。

## D-009（2026-08-19）角色改变弹幕（星辉进化树）

**决策**：成长系统不止数值（攻击 +10% / 生命 +5%），而是「**角色改变弹幕**」。以黎歌「星辉」为例的进化链：Lv1 基础星弹 → Lv2 开始追踪 → Lv3 命中产生星屑 → Lv4 星屑环绕玩家 → Lv5 形成星轨 → Lv6 星轨穿透 → Lv7 敌人死亡星爆 → 最终全屏「星之领域」。

**理由**：成长爽感 = 「我喜欢的魔女越来越强，我的弹幕长成魔法阵」。战斗三层爽点（操作→弹幕→角色）叠加，比单纯追逐"0 伤通关"更有商业意义。

**约束**：成长表**数据驱动**（.tres，不硬编码 switch 堆等级逻辑）；扩展现有 `PlayerController.ShotSpecs` / `ApplyUpgrade` 链；新系统（星屑环绕 / 星轨 / 星爆）按长期规划 v1.0 的特效分级（L0~L3）控制成本；**当前 M1-PERF 阶段只保证架构预留，不提前实现 Lv4+**。

## D-010（2026-08-19）移动端基调

**决策**：键鼠更精准、更自由；**触屏更智能、更容错**——手机端默认自动攻击 + 自动瞄准 + 轻微软追踪 + 简化技能释放。

**理由**：移动端受手指遮挡、操作精度、屏幕尺寸、长时间操作疲劳、横竖屏与设备刷新率差异限制；"纯小蜜蜂式硬核"不适合手机，「智能 + 容错」反而舒服。

**约束**：输入层走 Input Map（现 `Input.GetVector`），触屏虚拟摇杆是**新增绑定而非重写**；自动射击已是默认行为，移动端友好天然具备。

## D-011（2026-08-19）版本封板纪律：M2 RC + 内容冻结线

**决策**：将当前 **30/30 探针全绿**状态正式封板为 **M2 RC（tag= `m2-release-candidate`）**，基线定义：「战斗 + 割草 + XP + 升级 + 敌人类型 + 波次闭环」稳定。封板后至实机验收通过前，**只允许修 Bug / 调参数 / 调数值 / 改表现**；以下一律进入 M2.5 / M3 backlog，未明确解锁**不得接入主循环**：角色切换、僚机、技能系统、触屏、软辅助、无尽模式、货币、新 Boss、Music Timeline。`m2_powerup` / `m2_touch` 列为 **M2.5 预研**（允许保留探针与数据，不接线）。

**理由**：Agent 会把"能顺手做的东西"误当成"现在就该做的东西"（本次 `m2_powerup`/`m2_touch` 即典型）。封板 + 冻结线是在机制上阻止 scope 蔓延，把验证收敛到"实机手感"这一真问题。

**约束**：M2 实机验收只回答四问——想不想继续打 / 有没有明显变强 / 四种敌人有无区别 / 屏幕变乱还能不能看懂；四条成立即过。验收通过后按 **星辉构筑 → 技能循环 → 软辅助/触屏** 的顺序进入 M2.5（第一阶段 4~6 个真正改变战斗的强化即可）。任何改动须保持 30/30 探针全绿 + build 0 错误 0 警告。
